# B82 — External-owner Forget, Reveal or History Reset before Regenerate provider dispatch

A same-branch Regenerate request can be durably admitted and queued while another SQLite owner applies a privileged `CharacterKnowledgeForgotten`, `CharacterKnowledgeRevealed`, or `CharacterContextReset` operation. The original owner has an in-process context watcher, but a foreign SQLite writer is not required to notify it. The durable pre-provider dispatch fence must therefore reject a stale character knowledge epoch rather than infer that the absence of a local notification means the world is unchanged.

The three new application integration regressions create two independent `SessionTimeline` SQLite owners, admits Regenerate from the first, then forgets the original player `EventId`, reveals the hidden accepted message, or resets the character context from the second. The first owner's `ProviderDispatchFence::before_provider` refuses dispatch, without writing `RegenerateMayHaveDispatched`. Read-only orphan inspection returns `DispatchUnknown` and does not enqueue, register, or dispatch a provider. The original knowledge remains visible at its immutable historical revision, while the latest foreign-owner projection honors the explicit Forget/Reveal/Reset operation. The original request is explicitly abandoned and the durable terminal can be inspected.

This is a **pre-provider** privacy fence. It does not prove that an external Forget/Reveal/History Reset occurring after the durable dispatch marker will interrupt an already-running remote provider. Do not enable public Regenerate on this evidence alone.
