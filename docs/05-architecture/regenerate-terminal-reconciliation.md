# B67 — Pending terminal reconciliation after persistence failure

The authoritative terminal state of an admitted Regenerate request is a Timeline fact (`RegenerateAbandoned` or the canonical accepted reply). A transient `RequestOutcome` is **not** a durable receipt.

When `TextGenerationFailed`, `InternalError`, or `finish_cancelled` cannot persist `RegenerateAbandoned`, `RequestRecord` keeps a **nonterminal** snapshot, retains its registry entry and records the local pending terminal decision. It must not claim completion, release its discovery record or accept a late draft as an accepted answer. Failures of the SQLite append are not silently treated as cancellations.

An owner can explicitly call `ChatApiState::reconcile_pending_terminals()`. The registry clones its records *before* entering Timeline, never holding registry/record locks during the native SQLite append. The repair calls the same idempotent `abandon_regenerate_request` CAS used by cancellation. Only successful durability releases the volatile record and records the original error/cancellation outcome. A failed repair stays pending; an already-accepted reply causes a conflict rather than deleting effects. The operation **never** dispatches or replays a provider request.

A process crash loses only the provisional outcome. Upon restart, use the immutable admission receipt and `SessionTimeline::reconcile_regenerate` to inspect the canonical durable state. An operator can choose `abandon_regenerate_request` by the original child, RequestId and admitted selection for an unresolved request. Never reconstruct a false completed provider error from absent volatile state, and never retry an uncertain HTTP call.

Tests: injected SQLite INSERT abort, retry without revision drift, reopen after a lost volatile outcome, `finish_cancelled` repair, existing cancellation/acceptance winner and archive tests. This is an internal owner capability; no UI, automatic retry loop, public Regenerate action or background scheduler was introduced. A permanently unavailable database still leaves a visibly active request: durable resolution requires storage recovery/operator intervention. Outside-process exactly-once invocation is not claimed.

Cancellation refused by a native `Storage` or `ConcurrentWrite` failure records a provisional cancellation intent and returns the existing conservative `TooLate` result. A semantic `Conflict` (for example, a canonical accepted reply won the race) is **not** misclassified as a retryable storage failure. `ChatApiState::close` attempts one reconciliation pass after `cancel_all`; a continuing failure is logged and the record stays registered. Subsequent explicit repair can be invoked after the database recovers, without extending the public `CancelResult` enum or touching GUI code.
