# C2: explicit, generation-bound Python worker recovery

`AiSupervisor::recover_failed_composed(service, expected_generation, composition, models)` is an explicit recovery primitive for an observed **failed** Python worker. It does not retain old settings, schedule retries or create an alternative source of model selection. The application must supply a freshly prepared `RuntimeComposition` with exactly one selected `ModelActivation` per service.

The supervisor refreshes child liveness, acquires the appropriate topology-scoped transition lock, and verifies that the existing worker's observed service statuses still refer to `expected_generation` and are `Failed`. A healthy, stopped or already replaced generation is rejected with `ActivationSuperseded`. The candidate worker is private until its Python handshake, plugin discovery and **every** selected model's `initialize(model_ready=true)` have succeeded. Only then does the supervisor publish a new generation and `ModelReady` for its services. Split recovery touches only its selected service; shared recovery reinitializes the complete supplied service composition.

An unsuccessful candidate is terminated, the old failed generation remains current, `active_model` is unset and the service returns to `Failed`, not `WorkerRunning`. The failed attempt is observable through `last_error` and can be retried by a supervising caller using a newly prepared plan. Old generation IDs are never accepted after a successful replacement.

The API deliberately has **no automatic retry loop**. Retry budgets, backoff, selection rereads, revalidation of assets and runtime profiles, and approval are application orchestration concerns. In particular, device-specific activation must not silently switch to the generic/software path: `activate_hardware` has its own runtime execution and selection guard contract. The software recovery endpoint rejects a failed worker that carries an active hardware runtime profile rather than bypassing device validation. A guarded hardware recovery entry point and production reactivation from `RunningAiApplication` remain future work.

Verification: `tests/ai_supervisor_recovery.rs` uses actual Python mock TTS/ASR workers and installed-layer receipts to test shared and split recovery, wrong-generation rejection, failure of one selected model during candidate preparation, and the absence of false `ModelReady`/`WorkerRunning` status. Other supervisor tests retain the existing cancellation and stale-stream guarantees.

Still open under issue #24: bounded automatic retry/exhaustion with explicit stop semantics, hardware-verified recovery entry point, revalidation of current persisted configuration, cancellation of a recovery operation, and integration through `RunningAiApplication`/live speech. Neither a successful Python handshake nor an installed model is sufficient for runtime `ModelReady`.
