# C3 — Keep staged installation ownership while uv survives its Rust parent

Scope: `src/ai_runtime/layer.rs`, issue #42; stacks on PR #162. This extends the existing interprocess lock protocol without adding a PID lease, database, package dependency, or portable directory layout.

An installation reserves `.staging-<uuid>.lock`, takes its exclusive OS file lock and creates the sibling staging directory while that lock is held. For a nonempty package lock, before launching `uv pip install`, Rust clones the already locked file handle and supplies the clone as the child's **stdin**. The marker is a zero-byte regular file, so a child reading stdin observes EOF rather than interactive input. Ownership remains valid while either Rust or the uv child retains the duplicated/inherited handle, even if Rust exits abruptly. The OS releases the lock only after the last such handle closes. `LayerInstaller` otherwise runs the same uv command, with the existing no-config, no-deps, no-download and target restrictions.

Reclamation uses the existing separate `open_stage_owner()` / `try_lock()` operation. A new installation cannot reclaim the stage while uv still holds its inherited handle. Once uv exits, a later installation may acquire the exclusive lock and reclaim the orphan stage. The test performs a real Linux process-crash scenario: a Rust **test-harness parent** starts the real mock-uv executable and blocks in `publish`; the parent is killed after the child signals readiness; the child survives and the independent next installer preserves its staging. After the child exits, the subsequent installer reclaims it. Existing cancellation/timeout and concurrent-installer tests remain required.

A dropped future also must not remove a directory while a child still holds ownership. The RAII cleanup drops its own handle, then tries to acquire a **new independent** owner handle. It waits briefly for the child to terminate; if the child still holds the lock, it leaves the stage with its lock marker for a future scan rather than delete under an active child. This replaces the earlier eager remove-on-error, which could race delayed process termination after `kill_on_drop`.

## Safety boundaries and acceptance gaps

- The child is expected to retain stdin during its `uv pip install` work. An executable that deliberately closes/replaces stdin early is **not protected** by the inherited file handle; the scanner relies on the cooperative ownership contract. An independently running grandchild that did **not** inherit this descriptor is also not covered.
- The regression is executed on Linux using a real Python mock-uv child and actual OS file locks. Rust documentation specifies inherited/duplicated handle lock lifetime for Unix and Windows, but a Windows end-to-end process-crash regression has **not** been executed here; full platform parity is not claimed.
- A concurrent hostile actor replacing sibling lock entries, an untrusted/network filesystem with unreliable locks, an external executable that rewrites receipt paths, and atomic no-replace publishing under adversarial filesystem races remain outside this slice.
- The collector runs only when a later installation requires staging. No background process or storage registry is added. Legacy stages without lock proof remain untouched.
- Full #42 acceptance still requires package/voice-asset ownership and removal, supported model-family parity, real uv-managed runtime installation, and portable UI behavior. Keep #42 open.

## Windows fail-closed finding (2026-11-07)

An independent Rust 1.98.1 Windows GitHub Actions process test (run `42343170731`) falsified an assumption that held on Linux: after terminating the parent process, a second Windows process **acquired** the lock even though the child holding an inherited cloned handle remained alive. This means inherited stdin alone cannot certify liveness on Windows. The package-layer orphan scanner is therefore deliberately **disabled on Windows** until an OS-verified descendant-ownership protocol is added. When a Windows install is aborted or times out after uv was launched, RAII leaves its staging directory and lock marker instead of deleting files that a live child might still be writing; a normal returned `uv` process exit permits ordinary cleanup. This intentionally trades potential disk accumulation for preservation of active installation data. No automatic PID/age-based fallback is used.
