# C2: observable worker recovery exhaustion and interruptible attempts

A live speech worker recovery budget belongs to the application-owned watcher, not the Python SDK or `AiSupervisor`. Each failed **worker generation** has at most two recovery attempts. Shared TTS/ASR services attached to that generation share one budget; independent split generations have independent budgets. Observations for generations no longer in `Failed` are pruned. A changed selected model resets the budget, but unchanged settings cannot silently reopen it.

A recovery operation must not delay application shutdown or processing of updated settings while Python is still initializing. The watcher selects between cancellation, changed settings, and the pending recovery future. On an interrupt, dropping the unfinished recovery future cancels the pending operation; `WorkerProcess` is launched with `kill_on_drop(true)`, so an unpublished candidate process is retired. The current saved selection is independently checked by the supervisor immediately before publication. Neither a cancelled nor a superseded candidate may be reported as `ModelReady`.

`ServiceRuntimeStatus.recovery` is an optional, typed record of `generation`, `attempted`, `maximum`, and `exhausted`. It describes the **application** retry policy and never substitutes for the supervisor's `phase` or `last_error`. Failed services sharing one process generation observe the same retry state. `LiveSpeechRuntime::refresh()` preserves retry metadata only while that exact generation remains failed; a successfully initialized replacement gets a new generation and no exhaustion flag. The GUI speech-status formatter reports the exhausted count alongside the original fatal error. Unchanged refresh/retry state does not emit another watch update.

Tests verify shared-generation visibility, absence of redundant retry notifications, pruning of old generations, cancellation and saved-settings-change interruption of an in-flight mock future, GUI formatter output, and previously implemented real Python mock-worker lifecycle regressions. **Not yet certified:** production managed-Python plus persisted-settings end-to-end recovery, a production GUI smoke test, device-profile hardware recovery and complete historical Python 3.12 integration suite. Issue #24 must stay open pending these proofs.

## In-flight candidate cancellation and failed-generation status

During recovery of a known failed generation, the original `Failed` status and causal `last_error` must stay observable **until** every replacement model successfully initializes and the supervisor publishes the new generation. Unlike first-time activation, a recovery attempt does not transition the old generation to `Starting`. This avoids a cancellation trap: if a real Python `initialize` stalls and the watcher drops the recovery future, the candidate is killed, but the old worker remains eligible for the still-available attempt budget. A Linux integration regression blocks `initialize` in the actual Python mock process, cancels the Rust recovery task, confirms process termination through `/proc`, verifies failed-generation state and the original error, and successfully retries after removing the block.
