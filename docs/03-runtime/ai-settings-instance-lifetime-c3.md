# C3.2: persisted settings root ownership — first fail-closed boundary

A configured persistent NeuroMita application now acquires a permanent OS-level exclusive lock on the **injected** data directory before preset/settings constructors read or write it. The concrete directory comes from `ApplicationConfig::persistent*`, not from `cwd`, `$HOME`, or platform cache defaults. The settings repository exposes its actual root so `ApplicationLifecycle::start` can detect retargeting and also protect an externally assembled `SettingsConfig` using `JsonSettingsRepository`. A live `ApplicationOwner` holds the lock until Python workers and the final SettingsLifecycle flush finish. The stable `.neuromita-settings-lifecycle.lock` marker is not unlinked after release; replacing or symlinking the marker fails closed.

**Deliberate policy:** only one active or preparing persistent application can own a particular data root. A second OS process fails during configuration/start rather than using a stale `SettingsOwner` snapshot. A separate data directory remains independent. An offline settings import checks the same lock and refuses to overwrite active settings. `JsonSettingsRepository::inspect_for_maintenance` returns a validated complete persisted document while retaining the exclusive lock; it is only an *inspection snapshot*, not permission to unlink a model revision.

The lifetime lock does not replace installed revision leases or Python child Job ownership. It does not protect callers that mutate JSON files without using the cooperating APIs, or manual AI configurations pointing at unrelated roots. Direct `JsonSettingsRepository::save()` now requires a temporary exclusive root lease before writing. A running application instead uses the internal `LeasedJsonSettingsRepository`, whose save verifies the same root and retains its already-acquired lifetime lease; a separate repository in the same or another OS process cannot save while that lease exists. This does not fence custom `SettingsRepository` implementations or direct filesystem writes by non-cooperating tools. Until custom write paths, the authoritative launch/root boundary, and all Windows/Linux crash-ordering cases are proven, **physical uninstall and GUI Remove remain disabled**; #42 stays OPEN. Exclusive process ownership is intentionally more restrictive than multi-instance shared-read mode. A later multi-instance protocol must not weaken this gate without an authoritative persisted-selection transaction.

Native test coverage includes same-process and separate-process admission, OS kill/reentry, damaged marker rejection, conflicting offline import/maintenance, and retargeted root refusal. Windows must run these tests natively; Linux cannot substitute for Windows lock semantics. Current progress gate C3 remains 3/5.

The cooperative JSON writer is tested against a live local and foreign-process owner, including byte-for-byte preservation on rejection and post-owner-exit acceptance. The owner-bound repository never obtains a nested lock and validates the canonical destination root on every save. This limits persistence only; it does not authorize model revision deletion.
