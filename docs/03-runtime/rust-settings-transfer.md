# Перенос настроек Rust: полный backup, импорт и экспорт

**Статус:** реализовано для Rust core. Область: только offline-файлы. Исходный Python-код прочитан как контекст на коммите 9f1c66f4178d900e1a898d38bf5808d2fcd7bb86; его файлы и пользовательские settings не изменялись и не читались.

## Что переносится

Единица переноса — полный конверт настроек Rust: `schema_version`, `revision` и все секции `AppSettings` (`voice`, `capture`, `interface`). Документ с этим конвертом — законченный backup Rust-настроек: его можно импортировать на другой машине или в другой файл, и он же является обычным файлом `JsonSettingsRepository`.

Это не полный backup приложения. Сознательно не переносятся: Python settings из SettingsManager (другая модель, другие defaults и произвольные ключи), API-пресеты и credentials, OAuth-аккаунты, модели/ASR-профили, world-state и игровые сохранения, журналы установщика и любые секреты. Отдельная секция или фрагмент тоже не является переносимым документом.

Различие полного и частичного документа задано строго на уровне формата. Полный конверт содержит все три обязательные поля и все обязательные секции. Документ, который парсится как JSON, но не содержит весь конверт (например, только `volume` или объект preset), отклоняется как `NotFullSettingsTransfer`. Документ с `schema_version`, отличным от 1, отклоняется как `UnsupportedSchema`. Частичного или lossy-импорта нет: недостающие значения не восполняются defaults, а лишние ключи не отбрасываются.

## Схема 1 и отсутствие миграций

Поддерживается только `schema_version = 1`. Историческая схема 0 в Rust не существует, поэтому путь миграции v0 → v1 не изобретается. Python-поля не маппятся на Rust-секции: их имена, обязательность, типы и дефолты различаются, а молчаливый fallback запрещён архитектурой.

Файл будущей или неизвестной схемы (например, 2) не читается, не понижается и не исправляется. Импорт future-схемы завершается ошибкой до любой записи; существующий store остаётся нетронутым. Единственный способ поддержать новую схему — добавить явную миграцию в новой версии кода.

## Формат

Канонический экспорт — pretty JSON с завершающим переводом строки и фиксированным порядком полей:

    {
      "schema_version": 1,
      "revision": 7,
      "settings": {
        "voice": { "volume": 80, "in_launcher": false, "in_game": false, "voice": "default" },
        "capture": { "enabled": false, "interval_ms": 1000, "jpeg_quality": 80 },
        "interface": { "language": "russian", "font_size": 14 }
      }
    }

Строгий разбор отклоняет:

- неизвестные поля на верхнем уровне и внутри любой секции;
- отсутствующие обязательные поля;
- дубликаты JSON-ключей (в том числе на вложенных уровнях);
- значения, которые не представимы типами схемы (например, `volume` вне 0..=100, строка вместо числа);
- некорректные комбинации после типизированного разбора: пустой voice identifier, `interval_ms = 0`, `jpeg_quality` вне 1..=100, `font_size` вне 6..=96.

Ошибки, вызванные типами (значение не десериализуется в `Volume` и т.п.), классифицируются как `InvalidEnvelope`. Нарушения инвариантов уже декодированных значений — `InvalidValue`. `MalformedJson` означает синтаксически некорректный JSON, `NotFullSettingsTransfer` — чужой или частичный документ.

## Экспорт

`JsonSettingsRepository::export_to` и CLI `neuromita settings export --source STORE.json --destination BACKUP.json`:

1. строго читают и валидируют source целиком;
2. кодируют тот же канонический конверт, которым repository сохраняет файл;
3. атомарно заменяют destination.

Source проверяется до записи, поэтому битый или чужой файл не создаёт backup. Повторный экспорт тех же настроек даёт те же байты. Существующий destination заменяется явно; дописывания нет. Экспортированный файл загружается как обычный store и содержит `revision` исходника.

## Импорт и revision

`JsonSettingsRepository::import` и CLI `neuromita settings import --source BACKUP.json --destination STORE.json`:

1. полностью декодируют и валидируют байты source в памяти;
2. кодируют канонический конверт;
3. только после этого атомарно заменяют destination.

При любой ошибке разбора, схемы или значений файл destination не изменяется. Импорт заменяет весь документ и никогда не сливает секции. `revision` берётся из конверта буквально: не инкрементируется, не пересчитывается и не сравнивается с текущим. Это восстановление сохранённого revision офлайн-файла, а не откат revision работающего core.

Повторный импорт того же документа даёт те же байты и тот же revision, то есть идемпотентен; отдельного «already imported» состояния нет. Импорт другого документа заменяет предыдущий. `AppSettings` — единое значение без сущностей и идентификаторов, поэтому merge, разрешение ID-коллизий и частичное слияние не определены.

## Атомарная замена и сбои

Каждая запись (save, export, import) использует уникальный sibling temp `STORE.json.<uuid>.tmp`, создаваемый с `create_new(true)`. После записи и `sync_all` файл закрывается, затем выполняется rename поверх destination. Уникальное имя не позволяет двум writer'ам делить или усекать один temp; при завершённом rename destination всегда содержит один целый документ. При конкурентной записи без общего lock побеждает последний завершённый rename; межпроцессная блокировка не обещается.

Если запись temp или rename завершились ошибкой (например, destination открыт с `share_mode(0)` на Windows или является каталогом), собственный temp удаляется, а прежние байты destination сохраняются. После устранения причины следующая запись успешна, в том числе повторная запись поверх уже существующего файла.

Осиротевший temp от прерванного процесса загрузкой игнорируется и не удаляется и не очищается последующей записью: восстановление таких файлов — отдельная явная операция, а не побочный эффект загрузки. Синхронизируется только файл; гарантий power-loss или directory durability нет.

## Один владелец и offline-граница

Импорт и экспорт — файловые операции и не вызывают `SettingsApi` и не мутируют работающий core. Работающий core продолжает владеть своим revision и может перезаписать файл при следующем save/flush, поэтому перенос выполняется при остановленном приложении. После запуска `SettingsSource::Stored` загружает импортированный конверт с его revision и последующие изменения продолжают нумерацию от него.

CLI обрабатывает эти команды до проверки `GEMINI_API_KEY` и до создания provider/core: сеть и ключи не нужны. Остальной CLI генерации не изменён.

## Ошибки

| Ситуация | Классификация |
|---|---|
| не JSON | `MalformedJson` |
| чужой/частичный документ, нет обязательного поля конверта | `NotFullSettingsTransfer` |
| `schema_version` не равен 1 | `UnsupportedSchema` |
| unknown/missing/duplicate поля, неверные типы | `InvalidEnvelope` |
| недопустимые значения после декодирования | `InvalidValue` |
| IO/rename | `SettingsError::Storage` |

CLI печатает `Error: ...` в stderr и завершается с ненулевым кодом; destination при ошибке валидации не меняется.

## Сознательные ограничения

- Импорт Python settings, пресетов, credentials и world backups не поддерживается и не эмулируется.
- Схемы v0 и миграций нет; future-схемы отклоняются.
- Частичный или lossy-импорт отсутствует.
- Нет межпроцессной блокировки; при конкурентной записи действует last-writer-wins.
- Нет directory fsync, power-loss durability и шифрования; файл настроек не защищает секреты.
