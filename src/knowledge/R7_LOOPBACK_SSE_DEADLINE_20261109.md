# R7 — Loopback SSE deadlines, provisional previews and native continuation

**Scope:** Agent A Cycle67 backend-only executable acceptance evidence. The production providers, ResponseGenerator deadline, HTTP retry policy, request state machine, Timeline owner and settings authority are unchanged. This adds independent protocol-level tests, not a streaming implementation or an additional fallback.

`tests/rag_sse_deadline.rs` uses the stock `OpenAiProvider` under the real `ApplicationLifecycle` with actual HTTP/1.1 loopback sockets and explicitly enabled SSE. The server deliberately fragments SSE event lines into 7-byte transport writes. Every scenario uses the one admitted 850 ms deadline and bounded fixture timeouts; no external model credentials, simulated provider trait, network access beyond loopback or GUI is involved.

1. **Chat Completions provisional output:** two valid `data:` deltas construct a complete provisional JSON excerpt without a terminal `finish_reason` or `[DONE]`. The request observer sees `streamed_json` while the provider is pending. A held-open HTTP response crosses the deadline and terminates as `TextGenerationFailed(DeadlineExceeded)` with `ProviderTimeout`. Terminal request status has no `streamed_json`, `streamed_text` or public `preview_text`, and a separate fresh SSE request completes normally. Releasing the old socket to send a late completion cannot change the failed request.
2. **Responses provisional output:** the same rejection/recovery test uses `response.output_text.delta` and a late `response.completed`, proving the Responses protocol variant is subject to the identical deadline and provisional-state cleanup.
3. **Chat Completions native tool:** a complete streamed `calculator(2+3)` call is executed by the existing native tool, and the next actual HTTP POST includes the tool-call ID and result `5`. The provider's second SSE response emits a plausible complete JSON delta but withholds its terminal event. The original request reaches `ProviderTimeout` and cannot accept that provisional answer.
4. **Responses native tool:** the equivalent real `response.output_item.added`, `response.function_call_arguments.delta/done` stream results in a verified `function_call_output` on the second HTTP POST; an incomplete second SSE stream still expires under the original absolute deadline.
5. **Retry followed by SSE:** a real HTTP 429 with `Retry-After: 0` is retried once through the existing provider policy, then a successful HTTP 200 SSE emits a partial candidate without terminal completion. The deadline applies to both attempts; the partial output is not accepted. No mid-stream retry or silent promotion of the incomplete response occurs.

The tests specifically distinguish **provider continuation after a completed tool** from a **blocked tool future**. Existing `calculator` and `memory_search` operations are immediate; `web_search`/`web_reader` require public HTTPS and forbid loopback/private IP endpoints. Without an intentionally injectable tool executor or another non-production network bypass, these tests cannot deterministically block the native tool itself. The ResponseGenerator's `timeout_at` applies to the supported async future, but a non-cooperative OS worker is not forcibly terminated.

No claim is made about live public HTTPS/DNS, model services, arbitrary tool execution blocking, persistent token streaming to clients, cross-process source locks, or full user-facing R7 parity. R6/R7 remain **OPEN** and the acceptance matrix is unchanged at **16 PASS / 4 PARTIAL / 6 OPEN**.
