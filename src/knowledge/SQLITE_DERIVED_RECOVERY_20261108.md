# Cycle48 — explicit SQLite Timeline lookup-index reconstruction (D5/M7 slice)

**Scope:** a repair operation owned by `SqliteTimelineRepository`, not a second Memory/SessionTimeline source of truth. The repository persists canonical `timeline_events` (with each complete typed `TimelineFact`), branch lineage, receipts, and selected branch. Lookup tables `timeline_fact_keys`, `timeline_observers`, `timeline_acquisitions`, and `timeline_resets` are strictly derived from those events. Missing index rows can otherwise make existing events appear absent from `event`, `kind`, `knows`, or observer-filtered `read`. Reopening a version-2 database recreates a dropped index table but does not automatically restore its rows.

**New explicit repair API:** `SqliteTimelineRepository::rebuild_derived_indexes(&mut self) -> Result<(), TimelineError>`.

The operation takes **one `BEGIN IMMEDIATE` transaction**, validates the canonical persisted world through the existing `TimelineStore::load_persisted` owner, clears only the four derived tables, and runs the **existing** `index_fact` plus canonical observer materialization for every persisted branch and event. This is a deliberate administrative action, not a read-time fallback or an automatic startup O(N) scan. It never rewrites canonical event JSON, branch lineage/head, receipts, active selection, or increments the logical `timeline_revision`; no user Timeline event is invented. A failed decode/validation, SQLite trigger/insert, or transaction rolls back the entire repair and leaves the previously committed database state untouched. Reapplying a successful repair is idempotent in observable state.

**Proof:** four new SQLite repository unit tests establish: (1) dropped lookup table and deleted secondary rows survive reopening as missing, then explicit repair restores original `EventId`, direct observer visibility, knowledge and unchanged revision across a second reopen; (2) injected failure midway through secondary index insertion rolls back all index mutations and retains canonical fact/receipt/revision, then retry succeeds; (3) a removed reset barrier is restored so pre-reset knowledge does not reappear after reopening; (4) corrupt canonical fact JSON refuses repair without erasing existing derived entries, then corrected canonical content can be rebuilt.

**Limitations:** this is not a repair of malformed canonical `timeline_events`, broken branch graph/receipts, damaged SQLite pages, or missing session archives; it intentionally cannot recover the source of truth from derived indexes. It does not include an authenticated CLI/GUI maintenance action or automatic database consistency detection. The caller must arrange appropriate out-of-band maintenance authorization and choose to invoke the repair explicitly. Concurrent SQLite writes are serialized by the existing transaction; distributed writers outside its storage owner must still coordinate access. No Documents index or Agent B SessionArchive transfer is introduced. **Formal M7 and D5 remain OPEN**, pending full user-data restore/observability, broader corruption/IO matrix, and SessionArchive ownership.

## Cycle49 — trusted local inspect/confirmed repair

A separate **offline** CLI maintenance command is now available without launching the app, HTTP server, or GUI:

```text
neuromita timeline-index inspect --database /absolute/path/to/timeline.sqlite3
neuromita timeline-index repair --database /absolute/path/to/timeline.sqlite3 --confirm FINGERPRINT_FROM_INSPECT
```

The operator must **stop the application before repair**. This is trusted local filesystem access, **not a remotely authenticated API**; `--confirm` is an optimistic concurrency fingerprint, not a secret authorization token or cross-process application lock. It is deliberately never exposed through unauthenticated HTTP and does not become a background repair scheduler.

`inspect` opens an existing SQLite file in **read-only** mode; it never calls `SqliteTimelineRepository::open`, which would initialize missing schema tables. The canonical `TimelineStore::load_persisted` validates existing branches, events and receipts. The code materializes expected secondary rows with the **existing `index_fact`** algorithm in a separate in-memory scratch SQLite database, then compares all four derived tables with the source database. Missing tables, missing rows and unexpected rows are all reported. Inspection is bounded to 100,000 canonical events and 500,000 rows per derived table. It rejects orphan canonical event/receipt rows instead of silently ignoring them, and returns a fingerprint over the snapshot's full source metadata and observed derived rows. The fingerprint intentionally includes source contents, receipts, selection and revision as well as the derived indexes; this is stronger than comparing the logical Timeline revision alone.

Confirmed repair obtains SQLite `BEGIN IMMEDIATE` **before** re-evaluating the preview against the supplied fingerprint. Any intervening mutation of a source event/branch/receipt/selection or derived row fails with `ConcurrentWrite` and **no repair writes**. Only after successful comparison does the transaction initialize any dropped derived table and reconstruct the four lookup tables from canonical Timeline. Errors (including malformed canonical JSON, invalid persisted world or SQL write failure) roll back all changes. It returns a post-repair preview showing zero drift; an already-consistent snapshot is an idempotent no-op. Canonical `timeline_events`, receipts, branch metadata, active selection and logical revision are not changed.

**Operational limits:** No automatic SQLite page recovery, repair of missing/corrupted canonical events, SessionArchive transfer, live-application distributed lock, GUI confirmation or Documents index owner. An independently running process may still read during WAL maintenance; the operator is required to stop the app and avoid external writers. The SQLite writer transaction serializes database writes during the compare-and-apply critical section. This is a finite backend maintenance slice, **not full formal D5/M7 acceptance**.

## Cycle50 — standalone CLI process acceptance and schema-convergence safeguards

The trusted offline `neuromita timeline-index` CLI now has **five executable integration tests which launch the actual CLI process**, not only repository methods. They seed a real SQLite Timeline with an observed event, a `CharacterContextReset`, a subsequent observed event, and persisted append receipts. After dropping `timeline_fact_keys` and deleting observer/reset rows, `inspect` reports exact drift and leaves the missing table absent; `repair --confirm` with a stale fingerprint exits nonzero, while the inspected fingerprint rebuilds the indexes. After reopening the repaired SQLite database, both original EventIds, observed reads, pre-reset forgotten state, post-reset knowledge, all canonical event rows, receipts, branch metadata and logical revision remain unchanged. The executable also rejects a malformed source and a nonexistent database without creating a file.

**New protective behavior:** the optimistic fingerprint now includes the definitions of all Timeline-owned SQLite tables, indexes and triggers (`sqlite_master` objects whose name or owning table starts with `timeline_`) in addition to canonical/source data and index rows. A schema mutation after `inspect` invalidates confirmation even when all recorded rows are unchanged. The snapshot caps inspected schema objects at 10,000. This is still **not an authentication token**; it is a content-and-schema stale-write guard.

A repair cannot report success merely because SQL statements executed: after rebuilding, the same authoritative preview must report **zero drift**. If a database trigger inserts unauthorized extra secondary rows during reconstruction, repair fails and the `BEGIN IMMEDIATE` transaction rolls back completely, preserving the original damaged-but-not-further-modified state. The process integration fixture verifies this with a hostile `AFTER INSERT` trigger. This validation does not authorize deleting the trigger or rewriting canonical data.

The five process-level cases are: (1) clean read-only inspect/damaged inspect/confirmed repair/reopen with exact EventIds and receipts; (2) stale canonical and derived row confirmations; (3) malformed source and nonexistent-file rejection with failure exit codes; (4) stale schema DDL confirmation rejection; (5) nonconvergent index-repair rollback. The tests deliberately remove `GEMINI_API_KEY` to prove that offline maintenance does not initialize a text-generation provider or server. **GUI is out of scope.**

Still missing for formal M7/D5: OS-level exclusion of another active application process, canonical-source corruption/SQLite page recovery beyond fail-closed rejection, authenticated backup/restore of the complete user-data set, and Agent B SessionArchive ownership. D5/M7 remain OPEN; this is an independently proven recovery subcriterion, not full acceptance.
