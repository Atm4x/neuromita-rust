# Cycle48 — explicit SQLite Timeline lookup-index reconstruction (D5/M7 slice)

**Scope:** a repair operation owned by `SqliteTimelineRepository`, not a second Memory/SessionTimeline source of truth. The repository persists canonical `timeline_events` (with each complete typed `TimelineFact`), branch lineage, receipts, and selected branch. Lookup tables `timeline_fact_keys`, `timeline_observers`, `timeline_acquisitions`, and `timeline_resets` are strictly derived from those events. Missing index rows can otherwise make existing events appear absent from `event`, `kind`, `knows`, or observer-filtered `read`. Reopening a version-2 database recreates a dropped index table but does not automatically restore its rows.

**New explicit repair API:** `SqliteTimelineRepository::rebuild_derived_indexes(&mut self) -> Result<(), TimelineError>`.

The operation takes **one `BEGIN IMMEDIATE` transaction**, validates the canonical persisted world through the existing `TimelineStore::load_persisted` owner, clears only the four derived tables, and runs the **existing** `index_fact` plus canonical observer materialization for every persisted branch and event. This is a deliberate administrative action, not a read-time fallback or an automatic startup O(N) scan. It never rewrites canonical event JSON, branch lineage/head, receipts, active selection, or increments the logical `timeline_revision`; no user Timeline event is invented. A failed decode/validation, SQLite trigger/insert, or transaction rolls back the entire repair and leaves the previously committed database state untouched. Reapplying a successful repair is idempotent in observable state.

**Proof:** four new SQLite repository unit tests establish: (1) dropped lookup table and deleted secondary rows survive reopening as missing, then explicit repair restores original `EventId`, direct observer visibility, knowledge and unchanged revision across a second reopen; (2) injected failure midway through secondary index insertion rolls back all index mutations and retains canonical fact/receipt/revision, then retry succeeds; (3) a removed reset barrier is restored so pre-reset knowledge does not reappear after reopening; (4) corrupt canonical fact JSON refuses repair without erasing existing derived entries, then corrected canonical content can be rebuilt.

**Limitations:** this is not a repair of malformed canonical `timeline_events`, broken branch graph/receipts, damaged SQLite pages, or missing session archives; it intentionally cannot recover the source of truth from derived indexes. It does not include an authenticated CLI/GUI maintenance action or automatic database consistency detection. The caller must arrange appropriate out-of-band maintenance authorization and choose to invoke the repair explicitly. Concurrent SQLite writes are serialized by the existing transaction; distributed writers outside its storage owner must still coordinate access. No Documents index or Agent B SessionArchive transfer is introduced. **Formal M7 and D5 remain OPEN**, pending full user-data restore/observability, broader corruption/IO matrix, and SessionArchive ownership.
