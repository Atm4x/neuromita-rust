# R6 — Versioned canonical Documents corpus replacement (Cycle70)

`neuromita documents fork-replace` creates **one new, independent character Documents corpus root** while leaving the previous authoritative directory and its files untouched. It requires the exact SHA-256 of the named old `.md`/`.txt` document and an external, regular, canonical UTF-8 replacement file. A mismatched digest, unknown/unowned file in the original root, symlink, malformed path, invalid text, changed source, full corpus, or pre-existing output causes failure without deleting or replacing any old document.

```text
neuromita documents fork-replace --root /absolute/kind-docs-v1 --character Kind --name notes.md --expected-sha256 <64-lowercase-hex> --source /absolute/incoming/notes.md --output /absolute/kind-docs-v2
neuromita documents reindex --root /absolute/kind-docs-v2 --character Kind --revisions-dir /absolute/immutable-index-revisions
```

The operator must then **explicitly activate** the new revision through the existing running application's `/documents activate Kind EXPECTED_SETTINGS_REVISION /absolute/receipt.json` command. `SettingsApi` remains the sole authority for which root/index is selected. The old root and its original index are still independently valid, including for in-flight requests admitted before activation; there is no automatic cutover, silent index fallback, duplicate settings owner or deletion of the previous corpus. The old root offers an operator-controlled rollback target, but restoration also requires an explicit `reindex` or a still-valid old receipt and CAS activation.

The operation reads all known `.md/.txt` documents into a fresh, private sibling staging directory and replaces the named document **only in the staged copy**. It refuses original corpora containing other entries instead of accidentally discarding unrelated content. Each copied document is independently verified against the initial source inspection, the final staged corpus is re-inspected under the same 48-file/128-KiB-single/512-KiB-total/1024-chunk limits, the original corpus and replacement bytes are checked again before publication, and an atomic no-replace directory rename publishes the new root. Linux uses `renameat2(RENAME_NOREPLACE)`, Windows uses `MoveFileExW` without replacement, other platforms fail closed; Unix stages use 0700 directories and 0600 files. Files and staged directory are synced on Unix, followed by parent sync; a failure **after** the rename returns `PublicationUncertain` and does not remove the published version. On Windows, parent directory durability is not claimed.

This avoids the unsafe `stat`/`unlink` time-of-check/time-of-use pattern: no operation ever unlinks or renames the previously authoritative file, so a concurrent process replacing that file cannot cause this command to delete its replacement. **It is not an application-wide snapshot transaction**; an external writer can still change original documents after the final inspection or write into the new published directory. Operators must coordinate concurrent writers and safeguard the root paths. SHA-256 is content evidence, not signed provenance, and receipt creation is not itself SettingsApi activation. No PDF/Office ingestion, semantic embeddings, GUI workflow or full R6 acceptance is asserted; R6/R7 remain OPEN, formal 16 PASS / 4 PARTIAL / 6 OPEN unchanged.
