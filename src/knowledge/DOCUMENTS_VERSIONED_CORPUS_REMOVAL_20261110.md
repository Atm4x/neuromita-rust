# R6 — Versioned logical removal from a Documents corpus (Cycle71)

The trusted local operator command `neuromita documents fork-remove` constructs a **new** character Documents directory that excludes one specifically named `.md` or `.txt` file. It requires the SHA-256 of that document as observed in the original corpus. The operation **never removes, renames, or overwrites** any file in the old directory. A named file with a changed digest, a missing file, symlinked source, unowned root entry, unsafe path, or existing destination causes an explicit error and no new selected version.

```text
neuromita documents fork-remove --root /absolute/kind-docs-v1 --character Kind --name notes.md --expected-sha256 <64-lowercase-hex> --output /absolute/kind-docs-v2
neuromita documents reindex --root /absolute/kind-docs-v2 --character Kind --revisions-dir /absolute/index-revisions
```

After saving the emitted reindex receipt, a trusted operator may issue `/documents activate Kind EXPECTED_SETTINGS_REVISION /absolute/receipt.json` in the running application. That explicit CAS/flush step is the **only** operation that changes the selected root/index for new requests; requests already admitted against the old root retain their admitted selection. The old directory and its valid index remain available for later explicitly requested rollback. A removal that leaves no files is valid and yields an empty, source-verified corpus, never implicit fallback to another character's documents.

Removal and replacement now use the same privately staged, independently verified, no-clobber directory publication primitive: strict canonical character directory; no unowned entries; 48 files / 128 KiB per file / 512 KiB total / 1024 chunks limits; verified expected digest; reinspection of all remaining source bytes and staged documents before publication. A Linux `renameat2(RENAME_NOREPLACE)` or Windows no-replace `MoveFileExW` publishes the new directory. Unix file/directory sync and output-parent sync are attempted. A post-publication parent synchronization error is reported as `PublicationUncertain` and **does not delete** the possibly published output; this uncertainty is never represented as success. Windows directory crash durability is not asserted.

Executable evidence: real CLI subprocesses verify correct omission, old-index preservation and new-index retrieval, wrong digest/unknown name and existing output rejection, symlink/unowned entry rejection, and two simultaneous fork-removers competing for the same output. Deterministic Linux hooks additionally verify source mutation during staging, foreign destination appearing before the final rename, and postrename sync failure preserving the new directory. Existing fork-replacement CLI/race tests continue to execute against the shared primitive.

**Security and scope limits:** This is not deletion of the old corpus, erasure of previously generated LLM text, physical secure wipe, authenticated provenance, transactional multi-process snapshot, or permission to delete another application's files. A malicious external writer can mutate files between optimistic verification and publication; operators must coordinate writers. No second settings owner, automatic cutover, model-based Documents reranker, PDF/Office parser, or full user-facing Documents workflow is added. R6/R7 remain OPEN, overall matrix **16 PASS / 4 PARTIAL / 6 OPEN**.
