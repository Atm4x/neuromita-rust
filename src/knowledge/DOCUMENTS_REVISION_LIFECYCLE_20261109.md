# Agent A Cycle61 — Documents immutable revisions and explicit activation

## Ownership and effect

- Text under an explicitly configured character's existing absolute `.md`/`.txt` root is authoritative. It is never modified by these APIs.
- `knowledge::document_index::build_new_revision(root, character, revisions_directory)` prepares a **new, UUID-named, no-overwrite** derived JSON index. It does not replace the old index, change settings, issue model requests, or select a default document root. The revisions directory must already exist and be canonical, outside the source root. Index contents and original files are rechecked before the receipt is returned.
- The standalone trusted offline `neuromita documents reindex --root ABSOLUTE_CHARACTER_ROOT --character Kind --revisions-dir EXISTING_ABSOLUTE_DIRECTORY` outputs a JSON `DocumentRevisionReceipt` with `{character, root, index, fingerprint, documents}`. The fingerprint commits to the validated index model; it is **not** a signature or independent author authentication. The prior `documents build`, `verify`, `query` commands continue to work.
- `document_revision::DocumentRevisionApi` orchestrates verified index preparation and existing `SettingsApi` ownership; it is not another settings store, event bus, or document database. `prepare` requires no started application, `verify` rechecks the receipt against authoritative files, `status` returns `Disabled` or `Ready` and refuses invalid/stale active indexes. `activate(receipt, expected_settings_revision)` verifies the receipt and uses the settings owner's section CAS; `deactivate(character, expected_revision)` removes **only** that character's mapping. The original map and all global Documents limits are preserved. Callers explicitly invoke `SettingsApi::flush().await` if a durable save is required; do not report durable activation merely because the in-memory CAS succeeded. Activation is for **trusted local in-process callers** and is not exposed as an unauthenticated network or offline file-rewrite command.
- Generation continues to select one source from **request-admitted immutable settings**, not the latest global map when the worker is scheduled. A queued request admitted under v1 never silently switches to v2. If original text changes so v1 is stale, it terminates before the provider; a newly admitted request after activation may use the separately verified v2 index. Active index files are not renamed, rewritten or auto-discarded.

## Failure and concurrency boundaries

- Stale revision, missing/damaged index, symlink source, wrong character/root, forged receipt, or changed input results in a typed refusal before any settings mutation. CAS rejects concurrent settings changes with `SettingsError::Conflict` rather than replacing another editor's state.
- Two concurrent prepares create different UUID destinations. Existing index paths are never overwritten; no hidden reindex is invoked by ordinary generation. Failure before publication removes owned staging. A post-hard-link directory fsync failure can return `DocumentError::PublicationUncertain` while the new index may exist. The operator must independently reverify that path; never infer nonpublication or delete arbitrary files.
- The filesystem source validation is optimistic, not a cross-process writer lock. The generation handler revalidates source and index immediately before provider invocation; there is no guarantee against a writer racing after that check. Index content fingerprints are not signed provenance. A source change can invalidate **both** old and newly built versions until a fresh revision is prepared.
- This is an explicit backend-only lifecycle. No automatic ingestion, Slint UI, PDF/Office parser, document embedding provider, reranker, model-backed semantic ranking, or user-facing citation UI has been added. R6/R7 remain formally OPEN.

## Executed acceptance evidence

- Real `ApplicationLifecycle`/controlled-provider test: v1 admitted and blocked at provider, second request admitted with v1, source changed, v2 prepared and activated, old v1 request refuses before provider while new v2 request receives updated excerpt. Includes failed forged receipt, stale settings CAS, status, opt-out and independent second-character configuration plus `SettingsApi::flush`.
- Separate-process CLI tests: multiple revision paths without overwrite, repeat build preserving previous bytes, stale v1 refusal, new v2 verification after source update, rejects in-root revision destination and unknown character. Existing Documents CLI tests preserve Unicode, source mutation, corruption and concurrent no-clobber guarantees.
- Rust 1.98.1 vendored/offline checks are enumerated in the Cycle61 report. No GUI, Legacy/Obsolete, Agent B internals or dotnet tests/build.
