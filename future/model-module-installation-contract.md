# Контракт модулей моделей, оборудования и установки

Согласован с пользователем 2026-11-11. Это целевой контракт; наличие похожего типа в текущем коде не означает завершённую реализацию. Он уточняет модель PR #416 и заменяет смешение производителя GPU, вычислительной среды и реализации worker в одном `backend`.

Реализация отслеживается в [issue #417](https://github.com/Atm4x/neuromita-rust/issues/417).

## Примитивы

- **Hardware** — описание конкретного CPU/GPU: типизированный ID, производитель, архитектура и обнаруженные факты о возможностях. Коллекция Hardware не принимает решений о моделях. Одно физическое устройство не становится двумя устройствами из-за доступности CUDA и Vulkan.
- **ModelModule** — владелец описания своих моделей, правил совместимости, параметров и подготовки установки/запуска. Python и Rust реализуют общие внешние контракты, сохраняя собственную внутреннюю механику.
- **ModelDefinition** — объявленная модулем модель с устойчивой идентичностью и ревизией. Название не является идентификатором. Реализация Python/Rust — метаданные конкретной модели, не независимый переключатель режима.
- **ExecutionConfiguration** — явно выбранные Hardware, вариант исполнения и параметры. Вариант содержит допустимую связку вычислительной среды и её backend; произвольные сочетания не конструируются.
- **InstallComponent** — идентифицируемая зависимость установки: host модуля, Python-окружение/пакеты, native executable, runtime-библиотеки, веса и другие ресурсы. Идентичность включает необходимые версии, платформу, целостность и совместимость.
- **InstallPlan** — точный план подготовки компонентов для выбранной модели и конфигурации. Планы принадлежат модулям; общий исполнитель не знает правил конкретных моделей.
- **ModelSession** — созданный worker с подготовленной моделью и вычислительным контекстом. Получает Hardware при запуске и сохраняет привязку до явной переконфигурации.

ID моделей, компонентов и устройств имеют собственные типы. Известные варианты категорий представлены enum/структурами в Core и типизированными адаптерами в UI. Сериализация enum строкой не делает обычную строку внутренним контрактом.

## Значение backend

`HardwareVendor` описывает NVIDIA/AMD/Intel и других производителей. Он не заменяет вычислительный backend.

Нужно различать реализацию worker (Python/Rust), вычислительную среду (PyTorch/Burn/ONNX Runtime), конкретный backend/способ выполнения и выбранное устройство. ONNX как формат модели не равен ONNX Runtime и не является runtime CubeCL.

Наличие Burn не доказывает универсальность любой модели. Модуль объявляет и проверяет только реально поддержанные конфигурации. CUDA-only модель не считается совместимой с AMD из-за наличия другого runtime в приложении.

## Владение правилами и отсутствие универсального Resolver

Core вызывает общий интерфейс уже выбранного ModelModule. Конкретная реализация модуля:

1. Проверяет переданный Hardware и параметры.
2. Возвращает допустимые варианты/ограничения либо конкретную причину отказа.
3. Готовит install plan выбранной конфигурации.
4. Преобразует Hardware в собственное представление устройства при создании worker.
5. Подтверждает фактическую работоспособность после инициализации.

Общий Core не содержит таблиц `если model_id == X, использовать CUDA`, не угадывает реализацию по имени и не заменяет конфигурацию после ошибки. Если подходят несколько устройств/вариантов, выбор остаётся явным. Номер `cuda:0` — представление внутри соответствующей среды, а не универсальный физический ID.

Ограничения алгоритма и SDK принадлежат реализации модуля. Общая инфраструктура предоставляет факты и исполняет контракт; UI отображает результат и вызывает команды. Не дублировать модельные правила в GUI, общем Core и worker.

## Модуль доступен раньше inference-зависимостей

Модуль имеет декларативную и исполняемую части:

| Часть | Доступность | Ответственность |
| --- | --- | --- |
| Декларативное описание | До установки Python, весов и inference-бинарников | ID, названия, объявленные модели и требования для исполнения контракта самого модуля |
| Установочный контракт | После подготовки необходимого host | Подробный install plan, параметры и проверки выбранной конфигурации |
| Inference-реализация | После установки её компонентов | Инициализация, прогрев и операции ModelSession |

Декларативное описание входит в сам модуль и читается Rust без исполнения кода модели. Оно не является отдельным GUI-каталогом или вторым источником списка production-моделей.

Описание содержит **bootstrap-требования модуля**. Install plan содержит **зависимости выбранной модели**. Один список зависимостей не дублируется в двух местах.

Для Python-модуля bootstrap-требование указывает совместимый Python SDK host. В текущем приложении Python закреплён на 3.12; точная поставка и версия SDK принадлежат закреплённому компоненту host, а не выбору случайного системного Python.

uv — самостоятельный исполнитель операций установки Python/пакетов. Он не знает о Whisper/Fish Speech и не определяет зависимости модели: получает явные задания из плана. Подготовка uv и Python не требует работоспособного inference-worker.

## Симметрия Python и Rust

Общий контракт: подготовить доступ к модулю → запросить план → подготовить компоненты → создать ModelSession.

Python-модуль исполняет контракт через подготовленный Python+SDK, не импортируя отсутствующие тяжёлые inference-зависимости.

Для Rust-модуля, встроенного в приложение, установочный контракт может быть обычной Rust-реализацией интерфейса. При независимой поставке модуля контракт может исполняться небольшим готовым native executable. Пользователь не обязан устанавливать Rust или компилировать исходники.

Native executable установочного контракта обязан запускаться без ещё не установленных inference-зависимостей. Если он сам требует CUDA DLL, которые должен установить, контракт нарушен. Не требовать отдельный executable от встроенных модулей без необходимости.

Burn-backend, отсутствующий в собранном worker, не включается загрузкой исходного crate в работающий процесс. Докачиваемые компоненты — совместимая готовая сборка worker и/или поддерживаемые ею runtime-библиотеки с явным контрактом совместимости.

## Одна установка, разные исполнители компонентов

Общий InstallationOwner владеет операцией установки, журналом, отменой, завершением и наблюдаемым состоянием. Его план может содержать зависимости разных видов.

Специализированные исполнители отвечают за свои компоненты: Python host, Python-пакеты, native worker, runtime-библиотеки и ресурсы модели. Они не образуют независимые конкурирующие системы установки Python/native.

Для динамического Python-контракта операция имеет этапы:

1. Прочитать декларативное описание выбранного модуля.
2. Подготовить закреплённый host, если его нет.
3. Получить от модуля подробный install plan для явных Hardware и параметров.
4. Проверить и выполнить этот план.
5. Только после готовности обязательных компонентов разрешить создание сессии.

Ожидающий подробного плана bootstrap-этап не показывается как уже известный полный план. Preview без Python может показать декларативные требования, но не выдуманный точный результат исполнения Python-контракта. Если полный план необходим до подготовки host, он должен поставляться как проверяемые данные модуля.

Компоненты переиспользуются по точной совместимой идентичности. Частично подготовленные компоненты не делают модель Ready. Публикация проверенного компонента и активация полного выбранного набора имеют отдельные границы. Отмена не означает удаление чужих или уже переиспользуемых зависимостей.

## Worker и независимость сервисов

Владелец сервиса создаёт ModelSession с выбранными Hardware и конфигурацией. Последующие infer-запросы передают текст/аудио и параметры операции, а не заново выбирают устройство.

Один активный worker на сервис. Изменение ASR не должно пересоздавать неизменённый TTS, Embedding или Reranker. Замена выполняется после подтверждённой остановки старого worker того же сервиса. Ошибка не запускает другую реализацию или CPU-режим неявно.

## Критерии завершения

- [ ] AI Hub обнаруживает Python/native модули и их декларативные модели без установленного Python и inference-бинарников.
- [ ] Выбор модели доступен через функциональный presenter и один Core-owned контракт; GUI/TUI не создают независимые каталоги.
- [ ] Bootstrap Python+SDK проходит без импорта PyTorch и весов модели.
- [ ] Native установочный контракт доступен до тяжёлых runtime-зависимостей.
- [ ] Одна операция установки наблюдается и отменяется одинаково для обеих реализаций.
- [ ] Отсутствующий/неподдержанный Hardware, несовместимый runtime и ошибка подготовки дают явные результаты.
- [ ] План связан с выбранными идентичностями и не применяется к изменившемуся модулю/устройству/конфигурации.
- [ ] Запуск подтверждает выбранную модель, устройство и готовность; наличие файлов не подменяет readiness.
- [ ] Переконфигурация одного сервиса сохраняет остальные активные поколения.
- [ ] Проверки покрывают чистый профиль без Python, повторное использование host, отмену между этапами и неуспешный запуск без fallback.
